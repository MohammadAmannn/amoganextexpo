# Controlled Cross-Repository Upgrade Automation Guide

This document defines the automated, safe, and controlled cross-repository upgrade pipeline for `@amogads/ui` across all registered consuming applications.

---

## 1. End-to-End Upgrade Flow

```
+-----------------------------------+
| 1. @amogads/ui Release Published |
|    (e.g., @amogads/ui@1.4.0)     |
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 2. Read Machine-Readable Registry |
|    (consumers-registry.json)      |
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 3. GitHub App Authentication      |
|    (Ephemeral Token per repo)     |
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 4. Create Upgrade Branch          |
|    (chore/upgrade-amoga-ui-v1.4.0)|
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 5. Strict Dependency Bump         |
|    (package.json & lockfile ONLY) |
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 6. Safety Diff Boundary Check     |
|    (Zero edits to app/features/..) |
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 7. Consuming App CI Execution     |
|    (lint, typecheck, build, tests)|
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 8. Create Pull Request            |
|    (With release notes & diff)    |
+-----------------+-----------------+
                  |
                  v
+-----------------+-----------------+
| 9. App Owner Manual Review & Merge|
|    (No auto-merging permitted)    |
+-----------------------------------+
```

## 3. GitHub App Configuration & Minimum Permissions

Cross-repository automation uses a dedicated **GitHub App** (`AmogaDS Upgrade Bot`). Personal Access Tokens (PATs) are strictly prohibited.

### Required Permissions:
| Permission Category | Scope | Justification |
|---|---|---|
| **Repository Contents** | `Read & Write` | Check out consumer repository, create upgrade branch, commit updated `package.json` and lockfile. |
| **Pull Requests** | `Read & Write` | Open PRs, update PR body with release notes, and check mergeability status. |
| **Checks / Workflows** | `Read` | Monitor consumer CI runs on the upgrade branch. |
| **Metadata** | `Read-only` | Repository discovery and team assignment. |

### Secrets Configuration:
* `AMOGA_UPGRADE_APP_ID`: GitHub App ID.
* `AMOGA_UPGRADE_APP_PRIVATE_KEY`: RSA Private key generated by the GitHub App.

## 4. Application Code Protection Rules

The automation engine strictly enforces file change boundaries:

### Protected Zones (NEVER modified by automation):
* `app/*` (Routes, layouts, loading boundaries)
* `src/features/*` (Business features, store definitions, hooks)
* `src/components/custom/*` (App-specific proprietary components)
* `src/lib/*` / `src/services/*` (API clients, middleware, auth logic)
* `src/context/*` / `src/stores/*` (Application global state)

### Permitted Modifications:
* `package.json` (Only the `@amogads/ui` dependency version string)
* `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` (Resulting dependency lock graph)

> [!CAUTION]
> If any other file in the repository is modified during dependency resolution, the upgrade engine aborts the job immediately with a critical failure and does not push a branch or open a PR.

## 5. Pull Request Structure & Content

Every generated PR contains:
1. **Version Diff Header**: Explicitly stating Previous Version vs New Version.
2. **Release Classification**:
   - `MAJOR`: Warning alert highlighting possible breaking changes and migration links.
   - `MINOR` / `PATCH`: Backwards-compatible badge with change summary.
3. **Changelog & Release Notes**: Rendered directly into the PR body.
4. **CI & Safety Verification Checklist**: Documenting that only dependency files were touched.
5. **Testing Checklist**: Viewports (Desktop/Tablet/Mobile), Theme (Light/Dark), and core application flows.
6. **Rollback Instructions**: Copy-pasteable rollback command.

---

## 6. Manual Approval & Merge Governance

* **Zero Auto-Merge**: Automated PRs are created in standard review mode.
* **App Owner Sign-off**: Requires approval from the consuming repository's Code Owners.
* **Passing Status Checks**: Requires all CI checks (linting, typechecking, tests, build) to be green.

---

## 7. Rollback & Recovery Process

If an unexpected regression occurs in a consuming application after merging or deploying a new `@amogads/ui` version:

### Option A: Standard Rollback via CLI
```bash
# 1. Downgrade to previous known good version
npm install @amogads/ui@1.0.0

# 2. Verify clean build
npm run build

# 3. Commit and push
git commit -am "fix: rollback @amogads/ui to v1.0.0"
git push origin main
```

### Option B: Git Revert of Merge PR
```bash
git revert -m 1 <MERGE_COMMIT_HASH>
git push origin main
```
